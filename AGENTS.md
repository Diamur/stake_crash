# AGENT.md

## Название проекта

**MEP / GamePanel** — браузерная встраиваемая панель управления и статистики для страниц казино-игр, в первую очередь для `crash`.

## Назначение

Проект состоит из двух связанных частей:

1. **Frontend-часть** — скрипт и стили, которые работают прямо внутри страницы игры.
2. **Backend-часть** — PHP endpoint и MySQL-хранилище для приёма событий и сохранения настроек.

Это не отдельный сайт и не SPA-приложение.  
Основная логика работает в контексте страницы: перехватывает живые данные, отслеживает DOM, строит графики, показывает панель справа, воспроизводит звуки, хранит локальное состояние и умеет синхронизироваться с удалённым PHP backend.

Основная игра сейчас — `crash`. Поддержка других игр задаётся через список slug-значений в настройках.

## Что делает frontend-скрипт

Во время работы скрипт:

1. Перехватывает `window.WebSocket` и слушает входящие сообщения.
2. Извлекает игровые данные из payload.
3. Отслеживает идентификаторы раундов и связывает live-событие с завершённым раундом.
4. Встраивает фиксированную правую панель `#mep-control-panel`.
5. Следит за DOM-блоком с прошлыми результатами.
6. Поддерживает внутренний список результатов.
7. Показывает:
   - текстовую статистику
   - таблицу порогов `<= X`
   - число подряд идущих значений
   - график множителей
   - diff-график
   - статистику `>= 2` и `< 2`
8. Загружает историю через модалку сайта.
9. Сохраняет UI-state локально.
10. Отправляет live и batch-данные на backend endpoint.
11. Загружает и сохраняет настройки на backend.

## Модель runtime

### 1. WebSocket-слой

Скрипт патчит `window.WebSocket` и оборачивает:

- `addEventListener("message", ...)`
- `onmessage = ...`

Назначение:
- слушать входящие сообщения, не ломая нативную работу страницы

Основные обязанности:
- сохранить исходное поведение сокета
- безопасно парсить JSON
- читать `payload.data`
- распознавать `crashMultiplier` и `crashGame`
- обновлять `MEP.WS.last.*`
- генерировать браузерные события `MEP:crashMultiplier` и `MEP:crashGame`

### 2. Связка round/event

В проекте есть `MEP.WSLink`, который помогает связать видимый результат с завершённым round-like id, даже если live WebSocket уже переключился на следующий раунд.

Это важно для:
- корректного `event_key`
- backend dedupe
- правильной записи результата

### 3. Слой панели

Панель монтируется как фиксированный overlay справа.

Главный контейнер:
- `#mep-control-panel`

Содержит:
- шапку с версией, игрой, счётчиком и кнопкой настроек
- сворачиваемый блок истории и статистики
- таблицу трекинга
- diff-график
- блок `>= 2 / < 2`
- основной график
- модальное окно настроек

Панель является рабочим операторским интерфейсом, а не декоративным UI.

### 4. DOM-трекинг

Скрипт использует DOM блока прошлых результатов как рабочий источник видимых значений.

Базовые селекторы:
- `#main-content div.past-bets`
- `#main-content div.past-bets.svelte-3cv27h`

Слой должен:
- находить новые элементы результата
- извлекать текст множителя
- извлекать статус по классам кнопки
- поддерживать внутренний список результатов
- восстанавливать пропущенные результаты после пауз и загрузки истории

### 5. Загрузка истории

Скрипт умеет:
- нажимать кнопку истории
- ждать появления модального окна
- читать строки таблицы
- листать пагинацию
- добавлять историю в локальный state
- временно останавливать live tracker
- снова запускать tracker после завершения

Важно:
- повторный клик во время загрузки = abort
- tracker должен останавливаться на время history import
- история дедуплицируется по ключу строки

### 6. Слой статистики

Скрипт считает:
- raw-список результатов
- таблицу `<= X`
- число подряд идущих значений
- `>= 2` и `< 2`
- разницу между ними
- накопительную diff-историю
- SVG-график множителей
- SVG diff-график

## Потоки данных

### Live flow
1. Приходит WebSocket-сообщение.
2. WebSocket-слой извлекает идентификаторы и live-метаданные.
3. DOM tracker замечает новый результат.
4. Результат попадает в `MEP.State.list`.
5. UI перерисовывается.
6. Пороговые расчёты обновляются.
7. При необходимости срабатывает звук.
8. Результат может быть отправлен в backend.

### History flow
1. Пользователь нажимает «Загрузить с истории».
2. Открывается history modal.
3. Tracker ставится на паузу.
4. История читается постранично.
5. Значения вливаются в state.
6. UI перерисовывается.
7. Tracker снова запускается.

### Settings flow
1. Открывается окно настроек.
2. Загружаются текущие значения.
3. Пользователь редактирует поля.
4. Настройки сохраняются локально.
5. Настройки могут быть синхронизированы с backend.
6. Звуки пересобираются.

## Что делает backend

### `ping`
Проверка доступности endpoint.  
Возвращает `ok`, `pong`, `ts`.

### `track`
Принимает:
- одиночную запись
- batch через `items`

Ожидаемые поля:
- `x`
- `ts`
- `payload`
- при наличии `event_key`

Особенности:
- если `ts` не пришёл, backend ставит `now_ms()`
- в batch `ts` сдвигается на индекс элемента, чтобы не словить коллизию уникального `event_ts`
- вставка идёт через `insert_track_event()`

### `settings_save`
Принимает:
- `device_id`
- `settings`

Сохраняет JSON в `stake_settings`.

### `settings_get`
Принимает:
- `device_id`

Возвращает:
- `found`
- `device_id`
- `updated_at`
- `settings`

## Что сейчас относится к серверным настройкам

На frontend в `settings_save` отправляется `MEP.Settings.state`, а не весь `MEP.State`.

Это значит:
- обычные настройки панели уже синхронизируются через backend
- diff guide levels и часть UI-state живут локально через `mep_tracking`, если отдельно не встроены в серверную схему

### Правило
Не путать:
- **settings** — обычные серверные настройки
- **tracking / UI-state** — локальное состояние панели

## Diff graph guide levels (`+ / -`)

Diff-график поддерживает две ручные горизонтальные пунктирные линии:

- положительный уровень `+`
- отрицательный уровень `-`

### Назначение
Это визуальные ориентиры для анализа diff-ряда.  
Они не пересчитывают статистику, а только добавляют направляющие внутри SVG diff-графика.

### Состояние
Используются поля:
- `MEP.State.diffPosLevel`
- `MEP.State.diffNegLevel`

Тип:
- целое неотрицательное число
- `0` = линия отключена

### UI
Поля ввода находятся в заголовке diff-блока.

Критично:
- имена ссылок в `mount()`, `bind()`, функциях применения UI и render-логике должны совпадать
- если mount и bind используют разные имена, input виден, но state не обновляется

### Render
Линии рисуются в `MEP.DiffGraph.render()` как SVG `<line>`.

Требования:
- ось `0` остаётся центром
- `+` рисуется выше центра
- `-` рисуется ниже центра
- линии пунктирные
- линии не должны перехватывать pointer events
- масштаб рассчитывается относительно `maxAbs`

### Сохранение
Поля `diffPosLevel` и `diffNegLevel` должны участвовать в:
- default state
- save/load для `mep_tracking`
- применении UI после загрузки

### Что нельзя ломать
- diff density logic
- zero axis
- tooltip logic
- bar render
- persistence этих значений

## Правила разработки для агента

### 1. Делать точечные правки
Предпочтительны маленькие локальные изменения, а не большие переписывания.

### 2. Уважать границы модулей
- график → править `MEP.Graph` / `MEP.DiffGraph`
- история → править `MEP.HistoryLoader`
- UI → править `MEP.UI`
- sync → править `MEP.Sync`
- backend action → править `backend/scate/_ver/index_0.1.6.php`
- DB low-level → править `backend/scate/_ver/db_core_0.1.3.php`

### 3. Сначала сохранять поведение, потом улучшать архитектуру
В проекте важнее рабочий операторский сценарий, чем “красивая” архитектура.

### 4. Учитывать обратную совместимость
Нельзя бездумно ломать старый `localStorage`, старый JSON или backend payload.

### 5. Не удалять существующие комментарии
Разрешено добавлять комментарии.  
Удалять существующие — только по прямому запросу.

### 6. Не менять стиль именования без необходимости
Использовать текущий стиль:
- `MEP.ModuleName`
- короткие имена handler-функций
- явные имена UI-ссылок
- прямую процедурную логику там, где она уже принята

### 7. Сохранять браузерную совместимость
Не навязывать bundler/SPA/tooling-подходы без отдельной задачи.

### 8. Держать публичный API стабильным
Существующий доступ через `window.MEP`, `MEP.tracker` и похожие debug-entry должен продолжать работать.

## Известные паттерны поведения

### Deduplication
Live sync использует dedupe, завязанный на:
- `event_key`
- `gameId`
- `lastSentKey`
- inter-tab lock в `localStorage`

На backend dedupe дополнительно опирается на:
- уникальный `event_key`
- уникальный `event_ts`

### Reconciliation tracker
Если часть раундов пропущена, tracker сравнивает недавнее окно DOM и достраивает пропуски.

### Приоритет звуков
Если одновременно срабатывает несколько строк:
- `high` → приоритет у большего `X`
- `low` → приоритет у меньшего `X`

### Flash duration
Длительность подсветки строки зависит от настроек и может учитывать длительность аудио.
